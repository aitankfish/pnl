## Problem Statement

GitHub's primitives (PRs, issues, stars, code review, commits) were built for
humans. In the agentic era, agents generate code, papers, and ideas faster than
humans can review or trust them. Three gaps open that GitHub structurally will
not fill (it is a neutral utility, not a market):

1. **Provenance** — git tracks who changed a line, not the intent/model/parent
   ideas that produced it.
2. **Trust at machine speed** — stars are cheap, code review does not scale,
   citations are gamed. There is no machine-readable "is this actually good /
   did it hold up" signal.
3. **No home for intent** — there is nowhere for a *claim* ("this approach will
   work / will ship / will beat baseline X") to live as a first-class,
   resolvable object.

PNL wants to be the layer that fills these — "GitHub of the AI era" — NOT by
hosting code (git stays the code/version layer), but by being the
**trust + conviction + resolution layer on top of the world's code, papers, and
ideas**, agent-native via MCP.

Tagline: **GitHub stores what's been built. PNL prices what's worth believing.**

## Demand Evidence

Honest, founder-stated: **pre-demand.** Live markets (Humimal, BVI Belt,
PteracAI; pools ~0–0.03 SOL) are largely the founder seeding the lake plus an
early circle. No stranger-pull or unprompted agent activity yet. This is a
**deliberate future bet**, not a status-quo-demand play, and the founder owns
that framing. Implication: every "GitHub of the AI era" claim is a hypothesis to
instantiate, not a finding to scale. The near-term job is to make ONE loop real,
not to add surface.

## Status Quo

What a builder/researcher does today to get work seen, trusted, or funded: post
to X and hope, push to GitHub for slow/cheap stars, or pitch into gatekept
grants/accelerators/VC. None give a durable, skin-in-the-game signal of whether
the work is actually good, and none are agent-native.

## Key Reframe (the session's turning point)

The founder's correction: **the pieces already exist on PNL.** Verified in code:

- A **live GitHub integration** already ships, with a shared client + caching in
  `apps/web/src/lib/github.ts` (unauth 60/hr, `GITHUB_TOKEN` 5000/hr, Redis cache
  5–10 min — so read-scale and rate limits are already handled).
- Endpoints that exist today: the **commit list** at
  `api/research/[id]/activity`; and under `api/research/[id]/repo/*`: tree, file,
  search, branches, **PRs**, **issues**, and a **single commit** (`commit/[sha]`).
- **Not yet fetched:** releases, tags, or CI/check-runs. These are needed for
  milestone resolution and are a *small new endpoint* (same `ghCachedFetch`
  pattern as `repo/pulls`), not existing data.
- `githubUrl` is stored on the **research paper** (`apps/web/src/lib/mongodb.ts:806`),
  not on the Project schema.
- A market/project reaches its repo **through its cited thesis paper**: the
  `PaperCitation` link (`mongodb.ts:882`, `role:'thesis'`, `projectId→paperId`)
  gives **market → thesis paper → repo → live git data**, with **stake** on the
  market.

So every PNL project effectively already bundles **idea + repo + paper + money**.
The bulk of this is *re-wiring*, not inventing: today a project is a **one-shot
prediction bet that resolves once and dies**, and the git data that exists is
**inert** — surfaced only inside the paper's code browser, not used as a signal
that the project is alive, not driving resolution, not refreshing the artifact.
The honest exception: milestone resolution needs **one small new endpoint**
(releases/tags), so it is not *purely* arrangement.

## Resolution: the core mechanic, reframed

Resolution is the known hard problem (`docs/plans` / memory note: no resolver
crank, stuck markets). The funding reframe changes what resolution *means*:

- **Bet-on-outcome (today):** resolution = "did the vague future happen."
  Subjective, slow, gameable → markets stall and rot. This is the failure mode.
- **Back-the-builder (target):** resolution = "did the builder ship the next
  milestone," which **git can answer objectively** (a tagged release, a passing
  CI run, a hit benchmark). No human judge, no oracle fight.

The move from *predicting fuzzy futures* to *verifying concrete deliverables* is
the unlock, and git-verified milestones are the most agent-native resolution
there is: agent commits → CI passes → milestone settles → next tranche releases.

## Target User & Narrowest Wedge

**User:** a builder or research-minded developer (human or human+agent) who has a
repo and wants it seen, trusted, and eventually funded while they keep working —
not a one-time bet on whether it "succeeds."

**Narrowest wedge ("Project pulse"):** surface the git activity PNL *already
fetches* on the market/project page: last-active date, recent commits (from
`api/research/[id]/activity`), open PRs and issues. Data source is resolved via
the `role:'thesis'` citation → that paper's `githubUrl` (there is no
project-direct `githubUrl` today; adding one is optional later work). The instant
a project shows it is being actively built, it stops being a frozen bet and
becomes a living project you can watch. Reuses the existing `lib/github.ts` client
and `repo/*` + `activity` endpoints. No new infrastructure, no chain code.
(Releases/tags and "contributors" are NOT yet fetched — out of scope for Pulse,
pulled in for step B.)

## Constraints

- **Chain-adjacent caution** (`[[feedback_chain_adjacent_edits]]`): no edits to

  The funding/money-flow change is the only chain-touching step and is sequenced
  LAST.
- **Free + non-custodial** agent stance holds (`[[project_agent_strategy_free_open]]`):

- **`next build` hides type errors** (`ignoreBuildErrors`) — verify with real

## Approaches Considered

### Approach A: Project Pulse first (minimal viable) — RECOMMENDED as step 1
Surface already-fetched git activity on the project/market page.
- Effort: S/M. Risk: Low. Reuses: `api/research/[id]/repo/*`, existing project
  view, citation link to thesis paper.
- Pros: visibly turns a bet into a living project; days not weeks; no chain code;
  proves the "keep working" half of the vision immediately.
- Cons: on its own it is display, not yet resolution or funding.

### Approach B: Milestone Resolution first (the meaning-maker)
Creator declares 2–3 milestones; a git event settles each. Requires a NEW
`repo/releases` (and/or tags) endpoint first — this data is not fetched today.
Each milestone needs three things specified, or it stalls exactly like today's
markets:
- **Trigger:** v1 = a polling cron over active projects' repos (webhooks are the
  later upgrade; lazy-on-read is too unreliable for payouts).
- **Write target:** OPEN — does a resolved milestone write to the on-chain market
  (the stake lives on-chain) or to a parallel off-chain Mongo status? Today's
  "stuck markets" are an on-chain resolver-crank gap, so an off-chain flip does
  NOT settle the real stake. Must be decided before B is "off-chain."
- **NO path:** every milestone carries a deadline; absence of the git event by
  the deadline resolves NO. Without this, back-the-builder markets stall like the
  bet-on-outcome markets B is meant to fix.
- Effort: M. Risk: Med. Reuses: `lib/github.ts` client; needs new releases/tags
  endpoint.
- Pros: directly fixes the resolver-crank gap; converts content into settled
  bets. Cons: needs live projects with repos; resolution rules + the on/off-chain
  write decision need care; public-repo only in v1 (single server token).

### Approach C: Funding / back-the-builder first (the moat, premature)
Stake becomes capital released to the builder on milestones.
- Effort: L/XL. Risk: High (new economic model, chain contract, audit surface).
- Pros: the real long-term differentiator. Cons: touches the chain layer first,
  i.e. the most dangerous, slowest, audit-sensitive part, before the loop is
  even proven. Wrong order.

## Recommended Approach

**Sequence, not a single pick:** A → B → (auto-artifact) → C, money last.

1. **Project Pulse (A).** Connect existing repo activity to the project view.
   Projects become living. Off-chain, low risk, fast.
2. **Milestone Resolution (B).** Add a small `repo/releases` endpoint; creator
   declares milestones with deadlines; a git event (release/tag) resolves YES, a
   passed deadline resolves NO. This is the resolver crank with git as the oracle.
   Decide the on-chain-vs-off-chain write target first (see Open Questions) — if
   it must settle the on-chain stake, this step is chain-adjacent, not off-chain.
3. **Auto-artifact refresh.** Summarize recent commits into the paper/mission
   using the existing BYOK concierge LLM. **Author opt-in / review-gated** — a
   machine-written paper overwriting a human's is the highest trust risk in steps
   1–3; the LLM proposes, the author accepts. Keeps the knowledge base fresh with
   low author effort, not zero.
4. **Funding evolution (C), LAST.** Stake-to-back-the-builder, released on
   milestones. Chain-touching, audit-gated, built only on a loop that already
   works.

Rationale: matches the founder's "use what we have" instinct, makes resolution
tractable, respects chain caution, and defers the risky money layer until the
loop has proven itself.

## Open Questions

- **Resolution write target (blocking for B):** does a resolved milestone write
  to the on-chain market or to off-chain Mongo? The stake is on-chain, so an
  off-chain flip does not settle it. This decides whether B is truly "off-chain"
  and likely pulls in `plp_program` (chain-adjacent — needs sign-off).
- **Milestone declaration UX:** free-text + manual git-event mapping, or a
  structured "milestone = this tag / this release / this CI check"? Start with
  the simplest (a GitHub Release/tag exists) and expand.
- **A project with no cited paper has no repo link.** Do we add a project-direct
  `githubUrl`, or require a thesis paper to attach a repo? (For Pulse v1, route
  through the thesis citation and skip projects without one.)
- **Private repos:** the single server `GITHUB_TOKEN` only sees public/visible
  repos. v1 = public-repo only, or require a per-project install token.
- **Pre-demand risk:** does Pulse alone create any pull, or only make the founder's
  own projects prettier? Needs one real external builder to test.

## Success Criteria

- Step 1 done = open a real project, see live git activity (last commit, recent
  PRs, release) pulled from its linked repo, and it *feels alive* vs a static bet.
- Step 2 done = a new `repo/releases` (or tags) endpoint exists; declare a
  milestone on one project and watch a real git event (a tagged release) flip it
  to resolved with no human judging, with a deadline that resolves NO on absence.
- Whole-loop done = one project, by one builder, goes idea → repo activity →
  milestone resolved → artifact auto-refreshed, end to end.

## Distribution / Rollout

All steps 1–3 ship inside the existing Next.js app (`apps/web`) on the existing
deploy pipeline; no new distribution channel. Step 4 (funding) requires program/
contract work and its own audit + release gate — out of scope for this doc.

## Dependencies

- Existing GitHub integration (`lib/github.ts` + `repo/*` + `activity`); auth/
  quota already handled (token 5000/hr + Redis cache).
- Project↔paper↔repo citation link (`role:'thesis'`, already in place).
- **New for step B:** a `repo/releases` (and/or tags) endpoint — small, same
  pattern as `repo/pulls`.
- BYOK concierge LLM (already shipped) for the auto-artifact step.
- For step 4 only (and possibly step B's write target): program/contract changes
  + audit (chain-adjacent, explicitly gated).

## The Assignment

Before building anything: **run the loop once, by hand, on one real repo.** Pick
a project that has a linked repo, define 3 concrete milestones, and manually
confirm a git event proves each (e.g. "milestone 1 = v0.1 tag exists"). If that
feels alive and honest, the product is real and Project Pulse is worth building.
If it feels hollow, you learned it cheap before writing code.
